## 1. Question and scope

Can a bounded policy choose useful divisions of work, integrate their actual products, and retain a coordination method that helps on a different task?

Three questions have separate answers: does the runtime execute the declared organization; does the organization help task performance; does retained coordination help subsequent work? A working graph, a successful task and a learning gain are different observations.

Use small multi-module Python repair tasks as the first measurement environment. They give us executable artifacts, incompatible interfaces, real dependencies and an external functional checker without inventing a new mathematical language. This chooses the initial test environment, not a SWE-only architecture. Scientific investigations can use the same obligation/input/submission/join semantics, but their instrument and evidence validity need separate qualification.

Build on existing compositions, attempts, broker operations, context packets, artifacts and evidence. No permanent personas, general chat bus, new scheduler, new distributed database, broad reputation system or new agent framework. No learner rewrite, global template marketplace or automatic production promotion in this slice.

## 2. Runtime contract

### Plan and execution

A team plan is a versioned artifact containing a parent obligation, source snapshot, bounded child obligations, dependencies, ownership, input bindings, join rules and one root allocation. Each child has a concrete output contract and access to the bytes needed to perform its work. Natural-language reasoning may explain a plan, but it cannot replace those bindings.

The first profile, `team-work/1`, supports three shapes:

| Shape | Execution | Parent candidate |
|---|---|---|
| `single` | One worker may plan, edit, inspect public feedback and revise | Its complete source tree |
| `alternatives` | Two workers independently attempt the whole task from the same snapshot; peer answers initially withheld | One complete submitted tree, selected using public evidence only |
| `decompose` | Two workers own disjoint editable paths and share an explicit interface contract | Their patches applied to the same base, followed by integration checking |

The adaptive policy selects a shape and, for decomposition, the obligations, owned paths and interface commitments from visible task information. A graph selected by fixture ID is not adaptive behavior. The policy can choose `single`; tasks must not reward spawning by definition.

At most two active child workers, one integration owner and one plan revision. These are finite pilot ceilings, not claims about an optimal society size. A revision can replace a failed child or serialize the remaining work; it cannot silently restart all children, obtain a fresh allocation or erase earlier costs. Once the final candidate is frozen, no task changes are allowed after protected evaluation feedback.

Prefer compilation into existing `run/v1` sequence, parallel, invoke and join nodes. A `JoinNode` dependency barrier is not itself a proof that artifacts fit: compile the integration check as a real invocation and bind its receipt to the resulting artifact. If a substrate extension is necessary, demonstrate the missing operation and add it at the existing boundary; do not implement a parallel runtime beside it.

### Submission and integration

For node `v`, record `s_v = (plan_revision, node_id, input_digests, ownership_generation, output_digest, receipt_refs)`. A submission has been received when its bytes exist and its invocation is attributable. It is accepted for a join only when its input/version/ownership bindings still match and the declared checks have run.

For a parent obligation `O`, child outputs `x_i`, assumptions `H` and combination `J`, local acceptance of every `x_i` is insufficient. The join must inspect `J(x_1,...,x_n)` under `H` against the parent contract. In this experiment the check is executable. It establishes only the tested contract; it is not a proof of arbitrary Python correctness.

Apply disjoint patches to the exact base digest. A clean textual merge is merely assembly. Run public integration checks against the assembled tree; retain its digest, failing input and observed output when a check fails. A model can propose a repair or a targeted new diagnostic, but it cannot declare its own response to be an authoritative pass. Generated tests are development feedback. The separately protected final evaluator owns the measured outcome.

For alternatives, select one complete tree by frozen public-check ranking, then a deterministic tie rule. No combining the best files from different alternatives without recording that as a new synthesized candidate and checking it. Never select by held-out grades.

If public checks cannot resolve a disagreement, the join remains unresolved or delivers a provisional final candidate for protected scoring with that qualification. Consensus does not close the obligation. The evaluator may establish that this candidate passes the finite task; the transcript must not retrospectively pretend the team knew that before scoring.

### Information and recovery

All arms receive the same task, source, tool envelope, public tests and admissible evidence. Selective packet materialization may reduce duplicated context but cannot give the adaptive arm privileged oracle information. Record packet digests, source references and which peer outputs were visible at each decision. Do not expose test-family labels, hidden mutations, reference patches or protected evaluator files to participants.

Each child uses an isolated writable tree. Ownership fences the accepted submission, not merely a filename convention. On plan revision, retain unaffected submissions only when their relevant input and interface bindings remain valid. Conservatively invalidate all dependent children when the affected dependency set cannot be established. Reuse stale-looking work through explicit revalidation, not optimistic assumption.

Resume reconstructs the same parent, graph revision, finished submissions and pending broker operations. It must not resubmit successful operations to recreate context. Existing uncertain-effect handling remains authoritative: an ambiguous partially receipted operation may pause with visible liability. Team 01 must demonstrate genuine same-database resume after a completed child; it does not require solving the entire previously ledgered mid-send recovery problem.

## 3. What persists after the workers disappear

The durable product is a checked task artifact plus experience about a coordination plan. Optionally, development produces a `coordination-template/1` candidate: a parameterized composition, its applicability conditions, required input/interface bindings, checks, resource ceiling, supporting episodes and known failure cases. It is stored using existing artifact/capability facilities and remains experimental.

A template must describe a way to organize or check new work. Copying the solved patch, expected answer, concrete task ID or a full conversation is not that result. A useful template might say: bind the producer/consumer schema before independent edits, then exercise a boundary case through both modules. Its executable effect is the order of operations and checks on newly bound source, not the explanatory sentence.

Initially allow one template candidate, derived from development episodes only. Freeze it before evaluation/transfer. Input binding uses declared public structural requirements, such as named exported signatures and permitted ownership partitions. Exact task identity may be provenance but may not be the applicability rule. Unsupported semantic applicability claims remain hypotheses; when required bindings are missing or ambiguous, record refusal and use the cold policy.

For live acquisition, use broker-routed model inference on the actual development corpus to propose the executable template. Allow at most two construction attempts and select at most one candidate, using development evidence only. Keep both attempts and their costs. A developer-authored template can validate mechanics but cannot substitute for the acquired candidate. Limit calibration, diagnostics and continuity probes to a total of 24 live development episodes before freeze, with separately declared finite construction exposure inside the campaign grant.

The transfer run starts in a fresh process with an unrelated source snapshot and no previous worker transcript. It loads template bytes by digest, checks applicability, binds new inputs, executes the resulting composition and checks the final new artifact. Record whether the template changed an actual decision. Merely quoting its digest is insufficient.

Do not force a template. If development provides no eligible candidate, freeze `none`; warm and cold runs still complete with explicit fallback. That is a valid no-acquisition result. The worker may use authored templates only for labeled mechanism tests, never as model-acquired transfer evidence.

## 4. Workload and protected measurement

Freeze four task families, each with one development task, two evaluation tasks and one transfer task: 4 development, 8 evaluation and 4 transfer tasks. Each source tree should be small enough to fit the shared context envelope and large enough to contain a real interface or dependency. Choose concrete fixtures and exact counts before held-out scoring.

| Family | Intended pressure, not an answer supplied to the policy | Required apparatus control |
|---|---|---|
| Independent repairs | Two defects in disjoint modules with stable interfaces | Both local fixes are necessary for root success |
| Coupled interface | Producer and consumer must agree about representation, units or boundary semantics | Individually plausible/local-green patches fail together |
| Sequential discovery | A diagnostic result changes what should be repaired next | Blind parallel edits cannot substitute for the missing observation |
| Adequate single worker | A localized defect or misleading decomposition opportunity | A valid single-worker solution exists within the same envelope |

Public specifications must state intended behavior. Do not make tasks impossible by concealing requirements; hold out concrete test instances, not necessary user requirements. Development/evaluation/transfer variants must change relevant behavior or interface structure, not only identifiers or literals. State exactly how far they differ; four families are not evidence of broad generalization.

Use a small JSON input/output program ABI: the editable package computes a specified transformation, potentially through several modules. The candidate runs in the existing isolated execution profile and receives test inputs; an external protected oracle compares returned outputs with expected results. Expected answers, reference implementations and the authoritative checker are not mounted into candidate-controlled execution. A candidate's own `passed=true`, altered test file or process exit code cannot establish root success. This deliberately limits the first SWE environment to executable data transformations while keeping real multi-file repair and integration.

Use an independently implemented functional oracle or a transparent set of expected input/output cases that covers the claimed finite behavior. Each family needs an authored valid solution and a plausible invalid combined solution to validate the apparatus; keep these outside participant-accessible inputs. A reviewer verifies the oracle independently of solver code. Hidden tests run only after the candidate is frozen and provide no repair feedback during that episode.

Freeze source, public and protected tests, task membership, splits, prompt contracts, model/API configuration, seeds where supported, policy versions, resource ceilings, ranking and comparison rules in one manifest. Neither participant nor learner reads protected data. Environment/tool feedback available during solving is recorded and costed. A faulty oracle invalidates affected measurements; correct it under a new manifest and rerun the affected comparison, preserving old evidence.

The worker can tune task difficulty and per-request limits on development only. An all-tie or universally failing held-out panel is reported as low discrimination; it does not authorize silently replacing hard cases, changing the policy or adding more samples until a gain appears.

## 5. Arms, budgets and decisions

Use one model/configuration across arms to isolate organization first. Homogeneous model calls are not assumed independent.

| Arm | Policy |
|---|---|
| S | Strong single worker: iterative diagnosis, multiple edits, tool feedback, self-review and role changes in one continuing context |
| P | Two fixed independent whole-task attempts, then public-check selection; unused resources can support the selected attempt's bounded revision |
| T | The bounded adaptive policy in section 2, including choosing one worker and revising the plan once |

S receives the same high-level advice about dependency discovery and interface checking as T. Do not reduce S to a one-shot prompt or deny it a plan because T uses one. P receives genuine alternative attempts. The different context organization is part of the intervention; additional budget or tools are not.

For the main evaluation, run all three arms on all 8 tasks with 2 repeats: 48 episodes. Pair task and repeat IDs, counterbalance execution order and isolate mutable state. A fixed seed does not guarantee identical provider randomness; repeats are descriptive replicates, not an independence proof.

Starting ceiling per episode: 8 model invocations, 96,000 cumulative input tokens, 24,000 cumulative output tokens, 16 visible tool executions, 900 seconds wall time, 2 simultaneous child operations and 1 plan revision. Broker checking/integration/cleanup has separately reserved finite capacity inside the same root allocation. The worker resolves exact executable reservations, per-call token limits, tool timeouts, checker capacity and monetary/credit exposure on development; freeze those before the main run. The research grant must bound the entire campaign, including calibration and failed attempts. These ceilings describe demand, not permission to spend without a valid grant.

Reserve enough capacity for a final check and cleanup before admitting children. Do not spend a child's full allowance and then omit integration as an unaffordable afterthought. Any unused allowance stays within the original root. Count planning, synthesis, retries, repeated context, checker calls, cancellations and unresolved reservations. Report input/output tokens, model calls, tool executions, elapsed time and internal settlement separately; unknown provider billing is not zero cost.

Primary outcome: number of episodes whose frozen final artifact satisfies the complete protected task checker. A timeout, invalid candidate or refusal contributes zero; an infrastructure outage has its own flag and prevents an unqualified complete-panel conclusion. Report paired wins/ties/losses and resource vectors, including failures, for T versus both S and P. Local pass counts and graph size are diagnostic only.

Preselected finite-panel rule for a **broader trial**, not release: valid complete records and clean apparatus controls; T must either (a) solve strictly more episodes than each comparator, with aggregate model tokens and tool executions each at most 1.25 times that comparator, or (b) tie each comparator's solve count, use no more of either resource, and use strictly fewer model tokens. In both cases no task family may lose more than one solved episode against either comparator. A zero comparator resource total requires a zero T total for that resource. Unknown resource totals make the rule unevaluable. Publish the raw vector even when the rule rejects.

This is an engineering pilot decision rule with deliberately visible tradeoffs, not a calibrated statistical discovery claim. Do not report a general team advantage, confidence interval justified by treating task variants as independent populations, or LEARN-6 promotion. A latency gain alone does not satisfy this rule. If latency looks attractive, the next experiment compares the same policy under concurrency one and two before attributing that gain to reasoning rather than scheduling.

### Retention comparison

On the 4 transfer tasks, run S, cold T and T with the frozen development template, twice each: 24 episodes. Cold/warm T use the same policy, model, root budget and starting capabilities except for template availability. Retrieval, applicability checks, loading and binding consume the warm allocation. Any fallback remains in the denominator. No transfer feedback updates the template or selector during the panel.

Report complete-task wins/ties/losses and resources for warm T versus cold T and S. A promising retention result requires the same rule above against both comparators, with no family losing a solved episode. Also report template-construction cost separately and cumulatively over observed transfer use; do not hide it in a training-free label. If per-use savings exist, calculate the break-even reuse count from measured construction overhead and savings, without assuming future demand. Quality gains have no automatic token conversion.

## 6. Minimum implementation obligations

| ID | Delivery and mechanism-changing acceptance |
|---|---|
| TM-01 | Plan/shape validation and compilation; undeclared paths, missing inputs, unsupported joins and resource excess refuse before dispatch. A real policy response selects the executed plan. |
| TM-02 | Children use actual attempts/operations, isolated trees and byte-bound packets. Changing a submitted behavior changes the assembled task result; changing prose alone does not fabricate success. |
| TM-03 | Assembly plus real integration check; two local-green incompatible contributions fail the root join, and a corrected combination passes. The final grader executes the submitted tree, never an authored replacement. |
| TM-04 | One bounded revision, stale-submission fencing, cancellation/liability accounting and genuine fresh-process continuation after a completed child. Include retained unchanged work and invalidated dependent work. |
| TM-05 | Four-family corpus, public/protected split, independently checked oracle, source freeze and exact task membership. Mechanism controls and live outcomes are separate records. |
| TM-06 | S/P/T execute the same root task through one public experiment entry with identical resource authority. Fixed doubles test orchestration; live calls exercise planning and child work. |
| TM-07 | One optional development-derived coordination template, frozen applicability/bindings, cold/warm/S transfer and fresh-process use. Disconnect or alter its executable plan and demonstrate a resulting execution change; preserve refusal and no-candidate paths. |
| TM-08 | Standalone checker/replay reconstructs complete panel verdicts and resource unions from committed evidence. Detect a missing whole pair, wrong artifact/receipt binding and hidden answer selection. One operator view exposes graph, pending work, selected artifact, join result and costs. |

One public entry runs plan -> work -> integrate -> freeze -> evaluate -> disposition, and the campaign entry additionally runs development -> template freeze -> evaluation -> transfer. Use ordinary importable Python functions plus one CLI; names are engineering choices recorded before parallel implementation. No critical replay driver may exist only under a temporary directory. Report the highest phase actually completed.

## 7. Reuse map and engineering discretion

| Responsibility | Existing starting point |
|---|---|
| Composition and continuation | `src/settlement/run.py`: existing node algebra, eligibility, continuation and barriers |
| Work, ownership, accounting | `store.py`: investigation/attempt commands, generations, reservation and receipts; `broker.py` dispatch |
| Context and evidence | `context.py`: packet materialization/binding/revalidation; `evidence.py` and `artifacts.py` |
| Retained executable behavior | `capabilities.py`, `development.py`, representation retention as a precedent rather than a second copy |
| Comparison and status | `evaluation.py`, `trials.py`, existing operator projection and experiment patterns |

The worker chooses function names, minimal tables/columns, package layout, fixture semantics and developer ergonomics. Shared contracts and migration ownership must be settled before concurrent edits. Extend context with the smallest named team decision contract if existing packet kinds cannot express required bindings; do not hide team instructions in an unrelated development slot.

An in-memory toy graph beside the real broker does not meet TM-01–04. Conversely, a generic arbitrary-DAG editor, remote cluster orchestration, automatic schema inference, embedding database and custom theorem prover are unnecessary. Use the existing sandbox profile. Lack of real containment limits live generated-code execution to a genuinely disposable isolated environment under the applicable authorization; a shim is not containment evidence.

## 8. Interpretation and next decision

Accept the implementation when the central behavioral gates work at their declared real/doubled boundary. A valid negative experiment is complete. Minor findings enter the ledger and do not create another unrestricted audit.

If T helps but retention does not, retain the coordination runtime and revise template acquisition rather than inventing a self-improving learner. If warm T helps only familiar variants, narrow applicability. If S wins, preserve single-worker default and use teams for separately demonstrated latency or access needs. If all methods fail, inspect task solvability, context, tool semantics and model budget before interpreting an architecture result.

Stage 8.7's first learner intervention will be chosen from observed development failures: for example, contract discovery before delegation, targeted integration probes, or template refusal on changed assumptions. We cannot responsibly select its intervention or statistical trajectory budget from component tests alone. Stage 9 will consolidate these results with the live representation result; no stack rewrite is preselected.
