## The authority guard reads green over 11 failures

`tests/check_execution_authority.py` prints
`OK: every call carries authority` over **48 calls in 4 files**
(43 + 1 + 1 + 3), while **11 tests fail on exactly the property it claims to
enforce**. All four files it scans pass; none appears in the 259.

Verified at source:

```python
TARGETS = {"measure", "reader_echoer", "score_response"}
FILES = ["tests/test_s09_e2_scored.py", "tests/test_inv_b13b_replseed.py",
         "tests/test_ad01_panel_variation.py", "tests/test_ad01_experience_axis.py"]
```

`FILES` is a hardcoded literal list with no glob and no directory walk. The gap
is **structural, not a file-list oversight**: the guard matches an `authority=`
keyword on calls named `measure`/`reader_echoer`/`score_response`, but the
failures are raised from the method executor, whose surface is `run_policy_step`
and the trajectory use-policy callers — different names, different subsystem.
Broadening `FILES` alone would not help, because `TARGETS` does not name the
functions that actually raise.

Its sibling makes this sharper. `tests/check_e2_authority.py:6` documents itself
as "the same check `tests/check_execution_authority.py` does for
`run_policy_step`". `run_policy_step` appears **zero times** in
`check_execution_authority.py` — grep count 0. The docstring describes a contract
the code does not implement.

This is the project's named recurring failure — a check that reads green while
matching nothing — recurring inside the gate built for it, in the same run where
the reader-census guard failed for the same class of reason.
