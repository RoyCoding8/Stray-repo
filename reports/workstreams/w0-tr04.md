## 1. The constant observable, proven

### 1.1 The fixpoint in the checker

`experiments/representation/checkers.py:47` (`check_software`) returns `PRESERVED` on exactly two reachable branches:

```python
73	    if candidate.get("ops") == parsed_task["ops"]:
74	        if software.witness_holds(parsed_task, candidate_ops):
75	            return _report(PRESERVED, current, initial, "ok-incumbent")
76	        return _report(NOT_PRESERVED, current, initial, "witness-lost-agree")
```

and `_witness_verdict` at line 80 ends:

```python

```

`check_graph` (line 99) has the same two-preserved-branch shape at lines 120 and 124.

### 1.2 The fixpoint in the reducers

`experiments/representation/reducers.py:25` (`ddmin_reduce`) assigns `keep` from one place only:

```python
46	            if probe(trial)["verdict"] == PRESERVED:
47	                keep = trial_keep
```

and returns via one of three exits: `initial-not-preserved` (line 28, `keep` untouched, i.e. the whole task), `budget-exhausted` (line 37, `keep` is the last accepted value), `locally-irreducible` (line 57, same). `greedy_reduce` at line 61 is structurally identical (`keep = trial_keep` at line 82).

### 1.3 The control flow that makes it constant

Compose the two. `keep` starts as `list(range(count))`, so `build(keep)` is the task itself. `build` deletes only, so every later `keep` is a subset, hence monotone. Every subset that becomes `keep` did so at a line where the oracle already returned `PRESERVED`. So `result["candidate"] = build(result["kept"])` (line 164) is one of exactly two things:

- the whole task, on the `initial-not-preserved` branch, which reaches `check_software` line 73 and grades `ok-incumbent` provided the witness holds;
- a candidate the oracle already graded `preserved`, which reaches line 91 and grades `ok-preserved`.

`not_preserved` is reachable at lines 76, 86, 88, 90 only if the candidate is not a legal deletion of a valid task. A deletion-only walk on a well-formed task cannot produce that. The verdict is therefore a function of task well-formedness, not of policy behaviour.

### 1.4 The identity that closes it

The review's phrasing ("a reducer retains a valid incumbent") is right but incomplete. The stronger statement is that **the oracle and the grader are the same function**. `SoftwareOracle.check` returns `check_software(self.task, candidate)`; `trajectory._check` returns `checkers.check_software(task, candidate)`. So the verdict a trial is *accepted* on is the verdict the output is *graded* on. There is no independent grading axis to vary. This is stated independently in `experiments/ad01/experience_axis.py:8-12` and `experiments/ad01/control_distinctness.py:620-623`.

### 2.3 What it cannot do

**It measures the walk, not the decision.** The trace shows what a method did. It does not show what the policy chose, because the `method_id` and `max_queries` that select the method are excluded from the evidence leg by `VERBATIM` (`s09_e2_scored.py:_without_verbatim`, and the `_evidence` docstring at line 536 states the inversion explicitly: the old leg "rewarded the echo and refused the reader"). The repair moved the site from the action's inputs to the candidate the world produced, because `assessment_profile._resolve_method` refuses a policy-supplied candidate. That repair is correct and it is incomplete, because on this panel the candidate does not move either.

**It does not by itself separate a reader from an echoer.** `experience_axis.reader_echoer` (line 813) is the built-in attempt to answer that, and on this checkout it returns `{"scored": False}` for all five policies. See section 6.

So the review's "useful progress" is fair but understated in one direction and overstated in another. It understates the instrument: `query_trace` distinguishes six walk signatures and six quality values where the terminal flag distinguishes one, and it names `budget-exhausted`, which is a real intermediate failure mode with no terminal analogue. It overstates it in the sense that matters for TR-04: the instrument measures the walk, and TR-04's question is about the **decision**. The design below has to bridge that gap, and `query_trace` alone does not.

## 4. W2/E2 experiment design, ready to freeze

### 4.1 Hypothesis

Stated so that a null is a complete answer.

> **H1.** Given the same target task, the same eligible methods, the same budget and the same opportunity to draw experience, an arm that receives **relevant** experience from the development split produces a *different executed decision* (chosen `method_id` and `max_queries`) and a *different held-out reduction quality* than an arm that receives no experience or equally-sized irrelevant experience. **H1 is not the claim that it will help.** The design is valid whether the relevant arm wins, ties, or loses. The preregistered alternative is one-sided: H0 is "relevant experience does not change the decision", and a tie on decision with a tie on quality is a positive measurement of H0, not a failed experiment.

The reason field is folded in. The second, co-primary observable is the **reason distribution of the first three probes**, which is the "useful experience versus echoing" discriminator, because an echo reproduces the input's reason vector and a reader that re-routes does not.

### 4.2 Arms

Four arms, one per cell. All four are constructed by `e2_replication.build_arm` (line 241), so they share the constructor and differ only in their `observations` field.

| Arm | `observations` | Built by |
|---|---|---|
| `relevant` | measured verdicts **and reasons** from the same family's **dev** split | `measured_observations(source_task_ids)` (line 260) |
| `none` | `[]` | `learner.no_experience_experience` (line 257) |
| `irrelevant` | size- and record-count-matched, other family's dev split | `_irrelevant_observations` (line 270) |
| `shuffled` | the **relevant** arm's rows, permuted across `task_id` and re-grading the reasons against the shuffled task | new; see 4.7 |

`shuffled` is the fourth arm and it is the one that separates "used the experience" from "saw a plausible-looking block of tokens". `irrelevant` alone cannot do this, because an irrelevant block drawn from a different family has a different reason vocabulary anyway.

### 4.3 Treatment inputs, and the render fix

Every arm's prompt is `e2_replication.prompt_for` (line 312) = `learner.treatment_prompt` + `ADAPTIVE_INPUTS`. **One line changes**, at `learner.py:985-989`:

```python
[{"task_id": o.get("task_id"), "verdict": o.get("verdict"),
  "reason": o.get("reason"), "detail": o.get("detail"),
  "method": o.get("method")} for o in observed[-8:]]
```

`detail` and `method` are included because the r4 records show `method` is what names the policy that earned an outcome, and `control_distinctness.experience_varies` already reports `methods_named` for exactly this reason. Rendering nothing else keeps the three rendered arms (relevant / irrelevant / shuffled) byte-comparable in length, which is the confound `irrelevant_control_for` already sizes against.

**The prompt is otherwise frozen.** No other line differs across arms. That is checked, not asserted, by the treatment-receipt verifier in 4.5.

| Held | Mechanism |
|---|---|

| Eligible methods | `e2_replication.eligible_for(target)` (line 342), from `s09_e2_scored.control_candidates` |

| Assessment | One sealed grader, `s09_e2_scored._grade` → `checkers.check_*`, never per-arm |

### 4.5 Verification comes first, before any dispatch

This is the check TR-04's disposition demands ("Qualification should demonstrate that the intervention can reach decisions and that the measurement can distinguish known controls"). It is a **broken-arm check**, not a gate on results. It runs per arm, per target, before the arm is admitted to the campaign.

**V1. Treatment receipt.** For each arm, before dispatch, write a receipt containing: the exact prompt bytes and their sha256, the full `observations` list as rendered, the count of observations, the number of distinct `(verdict, reason)` pairs, and the number of distinct `reason` values. Then assert, on the receipt:

- `distinct_reasons >= 2` for `relevant` and `irrelevant`;
- `observations == []` for `none`, and `prompt_sha256` differs from `relevant`'s;
- for `shuffled`, `set(task_ids)` equals `relevant`'s and the mapping differs on at least one row.

**V2. Receipt-to-prompt binding.** Re-derive the `Prior observations:` line from the receipt's `observations` and assert it is a substring of the frozen prompt bytes. This is what makes "the arm received what we think it received" a measurement rather than a belief. An arm whose receipt and prompt disagree is a **broken arm** and the campaign refuses, exactly as `e2_replication.require_measurable_verdicts` (line 218) already refuses an unflippable experience.

**V3. Decision reachability.** Confirm the policy's chosen `method_id` is a member of `eligible_methods` and that the candidate the world produced is attributable to that choice. This is the `arms_execute_their_own_bound_policy` leg that r4 already passes, extended from "the arm executes its bound policy" to "the policy chose among them".

V1 and V2 are pure data checks over the receipt. They need no model. V3 needs an executed policy and is covered by the qualification in section 5.

### 4.6 Observables

**Validity conditions (must hold; failure invalidates the record, it is not a null).**

- V-a. The final candidate is a legal deletion and grades `preserved` (`checkers.is_legal_deletion` / `is_legal_subgraph`).
- V-b. The arm's treatment receipt passes V1 and V2.
- V-c. No fallback fired on the target (`use_error is None`, `fallback_reason == ""`).
- V-d. The record names an executed policy id. This is the defect `control_distinct` refused E2 for: `e2_replication` writes an `operation_id` and never an executed policy id. Fix by writing `selected_identity`, which `s09_e2_scored._execute` already returns at line 455.

**Primary benefit observable (non-constant by construction).**

- **P1. Held-out reduction quality**, `normalized_reduction = (initial_measure - final_measure) / initial_measure`, on the **use** split, sealed before the arm runs. Six distinct values already exist in r4, so this is not constant. This is the benefit metric.

**Secondary decision observables (these carry the "useful versus echoing" question).**

- **P2. Executed decision vector**, `(method_id, max_queries)`, from the action the policy admitted. Compared across arms, and under the verdict-flipped alternate view.
- **P3. Candidate moved under evidence**, `s09_e2_scored._evidence`'s `varied` bit. This is the existing evidence leg at its repaired site. A reader varies it; an echoer does not, because an echo cannot change what the method does.
- **P4. Early-failure reason vector**, the `reason` sequence of the first three `query_trace` entries. This is the "useful experience" discriminator. An echoer reproduces the input's reason distribution; a reader re-routes and produces its own.

**Full resource vector (recorded per record, never aggregated away).**

`model_calls`, `tokens`, `input_tokens`, `output_tokens`, `sandbox_ops`, `sandbox_units`, `witness_queries`, `charge_units`, `elapsed_s`, plus the `budget-exhausted` count from `query_trace`. Where a value is unknown it is recorded as the string `"UNCERTAIN"`, following the convention `cost.json` already uses for `lost_responses` and `provider_billing`. A spend that cannot be read is UNMEASURED and never zero.

**Terminal `preserved` is retained as validity condition V-a only.** It is not a benefit metric. It is one bit and it is constant on this world, so it cannot distinguish arms.

### 4.7 The `shuffled` arm, precisely

Take the `relevant` arm's observation rows. Permute the assignment of `reason` across `task_id` with a fixed seed derived from the freeze digest, then re-grade each row's `reason` by actually running the reducer on that task at the recorded `method` and budget, so the shuffled reason is a *true* reason for the task it is now attached to, not a fabricated string. The resulting block has the same tasks, the same count, the same character length, and the same verdict multiset as `relevant`, and differs only in the pairing between task and outcome.

A reader's decision should be sensitive to that pairing. An echoer's is not. A model that ignores experience is unaffected by both, which is the H0 prediction.

### 4.8 Decision rule, fixed before the run

Let `Q(a)` be the mean `normalized_reduction` for arm `a` over the sealed use tasks, in each namespace separately.

- **Positive.** `Q(relevant) > Q(none)` **and** `Q(relevant) > Q(irrelevant)` **and** `Q(relevant) > Q(shuffled)` in **both** namespaces, and the P2 decision vector differs from `none` in at least one target.
- **Null (H0 supported).** `Q(relevant) == Q(none)` within the pre-registered tolerance, and the P2 decision vector is identical on every target. Recorded as a complete answer. **This is a valid outcome and the run is not repeated to escape it.**
- **Negative.** `Q(relevant) < Q(none)` in both namespaces. Recorded as a loss, at the measured scope.
- **Inconclusive.** The namespaces disagree, or any V-condition failed. Reported as inconclusive, with the failing condition named. Inconclusive is not converted into a null.

**Tolerance is fixed in the freeze, not chosen after seeing results.** Proposed `1e-9` on `normalized_reduction` and exact equality on the decision vector. A tolerance picked after the data exists is the defect this whole lane exists to prevent; the `experience_axis.py:94-99` comment ("a budget chosen per call is a budget chosen after seeing the answer") is the precedent.

**Rejection is permitted and preregistered.** If `relevant` beats both controls in one namespace and not the other, that is a positive in one and a null in the other, reported as both. Replication is not a filter that selects for the favourable half.

### 4.9 Two independent namespaces

| Namespace | Mutable state | Assessment feedback | Panel |
|---|---|---|---|
| `inv_w2_e2_a` | its own disposable database | its own | `worlds_exp` (`ad01-exp-axis`) |
| `inv_w2_e2_b` | its own disposable database, different token | its own | a second freeze with a different digest and a different task draw |

Mechanism, all already in the codebase:

- `s09_run_isolation.create_disposable_db(token)` (line 249) creates a database whose name carries the namespace token, and `drop_disposable_db` (line 267) refuses to drop anything not marked disposable. Each namespace gets a distinct token.
- Each namespace freezes its own contrast body and records its own `freeze_digest` via `e2_replication.digest_of` / `verify_freeze` (line 148), which refuses a body edited after freezing.
- The two panels must differ in task draw, not only in name. A second digest over the same tasks is not a replication.
- Everything written under `reports/evidence/<namespace>/` is per-namespace. No cross-namespace write.

**A rerun after an apparatus failure is not replication.** If a run is voided for an apparatus cause (staging refusal, lost response, provider outage, deadline), it is recorded as `voided` with the cause, and the namespace re-runs as a **new** run id that is reported alongside the voided one. It is never counted as the second namespace, and never as a replication of it. `e2_replication.py:778` already states the governing rule for a lost response ("preserved as a null, never as a worse policy"), and `inv_r1_e2_gated/RESULT.md` is the template for how a void is written down.

## 5. Pre-spend qualification gate

The gate must demonstrate two things with **no model calls**: that the intervention can reach decisions, and that the measurement can distinguish known controls.

### 6.1 Two defects that block the qualification gate on Windows

`tests/test_ad01_experience_axis.py` on `dfbd557`:

```

```

- `test_the_instrument_separates_a_reader_from_an_echoer`
- `test_a_policy_that_re_routes_outscores_the_echoer`
- `test_the_candidate_is_where_a_reader_and_an_echoer_differ`
- `test_the_new_panel_regenerates_and_audits_clean`

**Both classes have one root cause: `core.autocrlf=true` with no `.gitattributes`.** Measured directly.

The three echo tests fail because `method_exec.py:1385` writes the staged driver with `driver.write_text(driver_source, encoding="utf-8")` and no `newline=""`. Python's text mode translates 16 LFs in `_STEP_DRIVER` to CRLF on write, and `_verify_operation_provenance` (line 876) then compares the sha256 of the **on-disk bytes** against the sha256 of the **in-memory string**:

```
template CR count 0   file CR count 16
expected e6a19a22661a3088   actual 05ef7fa4fbda681c
```

`byte-write matches template: True` confirms a `write_bytes` / `newline=""` write hashes correctly. `_execute` catches `MethodExecutionError` and returns `None` (line 441-442), so every policy is recorded `{"scored": False}` and `reader_echoer`'s `candidates_moved` key is never written, producing the `KeyError`.

The manifest test fails because `experience_axis.verify_freeze` (line 764) hashes `manifest.json` as read, and the checkout has 446 CRLFs:

```
pinned            89b0f3330ca644ee13a4
raw               f39c98b026368b352152
lf-normalized     89b0f3330ca644ee13a4
would-match-on-linux: True
```

**This is a real portability defect in the code the TR-04 experiment depends on, not a Windows-only curiosity to be waived.** The driver's own digest check is a sound invariant; the staging does not preserve it. Two options for the coordinator, and the second is better:
