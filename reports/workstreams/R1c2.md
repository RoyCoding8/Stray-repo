# R1c Part 2 — R01-006 / R01-013 / R01-014 recovery, continuation, deadline fixes

Branch: `codex/review01-r01-admit` (on `406e9ed`, R1a/R1b/R1c1 intact).
Scope: R01-006 (checkpoint/restore barrier + fence), R01-013 (typed outcome
consumption + durable workflow resources), R01-014 store side (deadline-bound
control-row waits) only.

Owned paths touched: `scripts/checkpoint.py`, `scripts/restore.py`,
`src/settlement/store.py` (`transact` deadline region, barrier/fence/verify
only), `src/settlement/broker.py` (workflow continuation regions only),
`src/settlement/run.py` (barrier/outcome-consumption regions only),
`tests/test_r01_recovery.py` (+ this report). Nothing else.

## What changed

R01-006 (`store.checkpoint_barrier` / `checkpoint_verify` / `restore_fence`,
scripts): `run_checkpoint` now establishes the domain barrier itself — one
journaled transition bumps `admission_epoch` and snapshots the journal count,
event epoch and undelivered outbox identities — then dumps, then refuses to
certify when anything moved (`barrier violated`, no manifest written).
Manifest carries `barrier`, `journal_count`, `outbox_pending` and a
`workflow` section; `--workflow-dsn` extends barrier, dump and verification
to the coordinated workflow store. `run_restore` keeps fresh-destination and
content checks, then establishes the execution fence before reporting
success: `restore_fence` bumps every live attempt's `ownership_generation`
and every in-flight operation's `_dispatch_generation` in one journaled
transition. Old dispatchers fail admission (`STALE_REVISION`) and old
post-send receipts land `unresolved` via the R1b generation check, never
`observed`. `run.suspend_for_barrier` records per-attempt suspension under a
barrier ref with a barrier-bound journal identity.

R01-013 (`run.operation_outcome` / `consume_operation_outcome`,
`broker.wf_consume` / `restore_workflow_resources`, `wf_record`): continuations
advance only from durable typed outcomes. `operation_outcome` reads the
operation row plus its receipts: success-only receipts complete the node;
any failure (without success) records a typed `node:outcome=failed`
observation and never completes; conflicting receipts stay `unknown`;
no-receipt outcomes derive from cancel/attempt state. `wf_consume` applies
this exactly once (completed-ref early-out plus per-receipt journal
identity). `wf_record` uses the same typed read when the operation row
exists and keeps the legacy summary path only for rows that were never
persisted. `restore_workflow_resources` rebuilds `ATTEMPT_WORKFLOW_RESOURCES`
from the attempt row and durable execution versions, refusing unadmitted
versions; `wf_ensure_dispatch` raises instead of `KeyError` when restoration
was skipped.

R01-014 (`store.transact`): every command sets `lock_timeout` and
`statement_timeout` from its own `deadline_ms` before touching the control
row; `LockNotAvailable`/`QueryCanceled` return `UNAVAILABLE_DEPENDENCY`
instead of blocking past the deadline.

## Open risks

- The checkpoint barrier detects concurrent writers and refuses
  certification; it does not block them. Hard quiesce of schedulers and
  executors stays operator duty (`suspend_for_barrier` exists per attempt).
  Admission-side refusal would need a schema flag outside owned paths.
- `pg_dump` and the post-dump verify are two steps: a transaction committing
  after verify is not caught. The window holds no lock; keep dumps quiet.
- Workflow coordination only happens when `--workflow-dsn` is supplied;
  DBOS deployments must pass their system DB explicitly.
- `statement_timeout` binds per statement; the monotonic deadline still
  bounds serialization retries, but the `UniqueViolation` re-raise path can
  propagate past the deadline (pre-existing).
- A genuine external cancel surfaces as `UNAVAILABLE_DEPENDENCY`; the detail
  names the deadline, which is the honest label for a bounded command path.
- `attempt_workflow` on a failed operation now ends `rounds-exhausted`
  instead of false completion. No auto-retry was added; the explicit
  `reset_dispatch` + `redispatch_after_reset` path remains the operator
  mechanism.
- Tests use fake gateways and `local-process` launches; no live provider or
  containment claim is made. Cross-process DBOS workflow restart was not
  exercised; `wf_consume`/`restore_workflow_resources` are plain functions
  and subprocess-safe by test.
