# Live repair vertical path (live2 campaign, development calibration)

One development task (`team01-t01`) through S/P/T plus three labeled
diagnostic probes, with repairs generated by live model calls through
broker-routed operations. No reference trees are loaded in this path
(`solver.py` has no `prepare_tree`/`_tree_files` use); child submissions
carry constructor-returned bytes, traced by operation id to gateway
receipts. An independent reviewer re-verified the S-episode chain
(response bytes digest == submitted digest `940f57aa…`, no family/kind
labels in prompts, substitution bytes followed to scored failure).

- `episodes/`: 6 episode records (S/P/T success 6/6 protected each;
  substitution failure; disconnect refusal; incompatible failure after
  one bounded rework repair round).
- `calls/`: per-call prompt/response/parse files (`<episode>__<op>.*`).
- `runs-manifest.sha256`: the 4.1 MB `runs/` bulk (sandbox envelopes)
  by hash, kept in the run area, not committed.
- Model/config: `muse-spark-1.3-contributor-free`, responses API,
  `reasoning_effort=low`, same task/source/tool access and per-episode
  bounded allocations for all arms.

Known observations (not defects): P's two independent attempts converged
to byte-identical repairs twice (same model, near-identical prompts);
the substitution fault was repaired to success on one run and stood as
failure on the next (repair call returned empty); the repair round could
not restore the renamed entry point in one attempt.
